# Canonical gesture portability proof

This runner compiles the existing gesture state machine and runs its existing assertions in a temporary, dependency-free Swift package named `MouthtypeCore`. It reads the canonical files under `Sources/` and `Tests/`; there is no second checked-in implementation, API extraction, or change to the app's package graph.

The current boundary is eight gesture source files importing only Foundation, with three canonical test files importing Foundation/Testing/MouthtypeCore. The 76 existing tests cover hold/release duration, double-tap locking, single-press toggle, repeated key-down suppression, Escape cancellation, dirty-state recovery, mouse interaction, and recording-length decisions. Events are synthetic domain values. Their Mac-derived key-code constants do not establish a Linux keyboard mapping or global shortcut implementation.

Run the script's own no-Swift orchestration tests with `python3 -W error::ResourceWarning -m unittest discover -s tools/linux-gesture-proof -p 'test_*.py'`.

Run the canonical package with `python3 tools/linux-gesture-proof/gesture_proof.py --receipt .planning/gesture-proof.json`. It uses the available `swift` executable, creates and deletes its own temporary package/build directory, and writes a new receipt without replacing an existing one. `--swift` can select a toolchain executable. No editor or app opens. No Apple/model dependency is downloaded because the generated package has only the canonical source/test targets.

For an actual Linux result, use `python3 tools/linux-gesture-proof/gesture_proof.py --require-linux --receipt .planning/gesture-linux-proof.json`. This rejects a macOS host rather than labelling its build as Linux evidence. A successful macOS run is useful host validation only.

`canonical.json` explicitly lists all selected files. The script compares it against every Swift source below the gesture directory and the Core tests that reference the gesture types or use gesture/hotkey/toggle filenames. Added, removed, or renamed related files fail inventory validation until reviewed. Unsupported imports also fail before invoking Swift. The exact bytes read are copied into the temporary package and hashed freshly into the receipt. The receipt records actual OS/architecture, Swift version, every canonical file digest, declared/executed test counts, status, duration, and compiler/test output. These current tests are not parameterized; a changed test-discovery format or invocation count requires updating this bounded proof instead of silently accepting missing assertions.

The Swift test command is capped at 180 seconds by default, configurable with `--deadline-seconds`. A separate bounded version probe precedes it. Success, compiler failure, timeout, Control+C, and termination clean up the generated package; subprocess groups are terminated with a bounded kill fallback. Exit 0 means the compile/test command succeeded and all declared tests were observed. Exit 1 reports failed, unavailable, cancelled, or timed-out execution. Exit 2 reports invalid inventory/configuration. No watcher, daemon, model, recording, desktop session, or clipboard is involved.

## Linux CI provenance

The narrowly scoped workflow uses the [official Swift container](https://www.swift.org/install/linux/#container), `swift:6.2.4-noble`, pinned to registry manifest digest `sha256:eccc7a97f9b9881d9659e2e788081fd7675f86d39793b51200bfb178398b3784`. Its Linux amd64 manifest is `sha256:1129f7d0490dc1d55a39aabe386f126821b1a5c70c5618b920f9138fd16c257d`. The [official image listing](https://github.com/docker-library/official-images/blob/master/library/swift) maps that tag to swift-docker revision `ef2c1e72ea88715a5b8c632b26bbf835a0c7bf4b`, directory `6.2/ubuntu/24.04`; the [pinned Dockerfile](https://github.com/swiftlang/swift-docker/blob/ef2c1e72ea88715a5b8c632b26bbf835a0c7bf4b/6.2/ubuntu/24.04/Dockerfile) installs the signed Swift6.2.4 toolchain. Registry provenance was inspected on2026-10-16 without pulling or starting the image locally.

The job runs on an Ubuntu24.04 x86_64 hosted runner with Docker `--init` so orphaned build children are reaped. A diagnostic run without init reproduced a killed Python descendant remaining as a zombie under the container’s sleeping `tail` PID1; the cleanup assertion still requires every owned PID to disappear. The job uses pinned official checkout/Python actions, has `contents: read`, persists no Git credentials, and has a ten-minute overall deadline. Its receipt metadata is printed in logs for verification. Python setup supports the temporary-package validation script; it does not add an app/runtime dependency. No private planning data, models, secrets, publish step, or release permission is used.

Only a completed, fetched CI log establishes actual Linux Swift compilation and test execution. Before that result, Linux execution remains pending. Passing this proof still does not establish that the full `MouthtypeCore` dependency graph builds on Linux, or prove Linux audio, portals, global shortcuts, text delivery, GUI, distribution packaging, model inference, or Arch compatibility. Those roadmap acceptance items stay separate.
